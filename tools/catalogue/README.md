# Task catalogue generator

`generate.py` writes the Flow task catalogue pages in `flow/catalogue/` from the task seed in `boomerang-io/flow.service.workflow` at a release tag. Run it at each release, as you regenerate the API reference. It needs Python 3.9 or later and git, and uses only the standard library.

## Run it

From the docs repo root:

```bash
git -C ../flow.service.workflow fetch --tags
python3 tools/catalogue/generate.py --flow-repo ../flow.service.workflow --tag 5.0.0-beta.39
```

| Option | Default | What it does |
| --- | --- | --- |
| `--flow-repo` | required | A clone of `flow.service.workflow`. The working tree isn't read, so it can be on any branch. |
| `--tag` | required | The release tag the docs describe. |
| `--out` | `flow/catalogue` | The folder to write to. |
| `--notes` | `tools/catalogue/notes.json` | The hand-kept notes. |
| `--check` | off | Writes nothing. Exits 1 when a page differs from what the tag generates, or a page is stale. |

It prints the task, category and revision counts and the number of notes applied, and prints any warning to stderr. It exits 1 without writing anything when the source or `notes.json` doesn't parse, or a note names a task, revision or category that isn't in the catalogue.

## What it reads

All with `git show <tag>:<path>`:

| Path | For |
| --- | --- |
| `service-core/src/main/resources/seed/tasks.json` | Each task's slug (`name`), type and status. |
| `service-core/src/main/resources/seed/task-revisions.json` | Each revision: `parentRef` (the task's slug), `version`, display name, category, description and `spec` (`params`, `results`, `image`). |
| `service-core/src/main/resources/seed/settings.json` | `default.image`, the image a `template` or `script` task runs on when its revision names none. |
| `service-dispatcher/src/main/resources/application.properties` | `flow.dispatcher.artifact.image`, the image the artifact tasks run on. |

The seed already has the effect of the migrations that rewrite seeded revisions after install: `_0043` (unpins task-flow images), `_0044` (Box `privateKey` is a password) and `_0045` (clears placeholder defaults). The generator reads the seed as it is.

### Tasks only a migration adds

A task that a migration inserts, and that isn't in `seed/tasks.json`, is listed by hand in `notes.json` under `migrationTasks`, with its params read from the Java source. At 5.0.0-beta.39 these are `upload-artifact` and `download-artifact`, from `_0018__SeedArtifactTasks.java`.

For each one, the generator checks that the migration file exists at the tag and that the task's slug, type, display name, param names, param labels and result names all appear in it as string literals. It warns when one doesn't, so re-read the Java. If the task has moved into the seed, the seed is used and the generator warns you to remove the entry.

## What it writes

- `overview.md` (title **Task catalogue**, menu label **Overview**): the intro, one row per category in palette order with its tasks, and how to read an entry.
- One page per palette category, named from the category, such as `communication-with-slack.md`. The order is the palette's: `Workflow` first, then the rest by plain string comparison, as the webapp sorts them. Within a page, tasks are sorted by display name.

Each task shows its latest revision: description, slug, type, revision number, image, notes, then a parameters table (label, name, type, required, default, helper text) and its results. A task with a `usage` entry in `notes.json` then has an "Example" and a "Common problems" subsection. A task that isn't `active` is listed under "Not in the palette" instead.

- **Labels and text** are quoted verbatim from the seed. Only pipes and `<` are escaped, and line breaks in a table cell become `<br>`.
- **Type** uses Task Manager's names for field types. A `password` field shows as "Secured".
- **Default** is blank when there is none. A secured field's default is shown only when it's a parameter reference such as `$(workspace.params.github-token)`; any other value shows as "Set, not shown".
- **Image** depends on the task type:

  | Type | Shows |
  | --- | --- |
  | `template`, `script` | The revision's image, or "Default task image" when it names none. |
  | `ai` | The revision's image. |
  | `custom` | "The image you set on the node", unless the revision names one. |
  | `uploadartifact`, `downloadartifact` | The dispatcher's `flow.dispatcher.artifact.image` and its default. |
  | Types Flow runs itself | "None. Flow runs this task itself." |

Every generated page has the frontmatter `title`, `order` (`overview.md` is 1, the categories follow from 2), `description` and `verified`, the `--tag` value quoted, which the website shows as "Verified against Flow …". It then carries the comment `<!-- Generated by tools/catalogue/generate.py from flow.service.workflow <tag>. Don't edit by hand. -->`. A page in the output folder with that comment that this run didn't produce is deleted, so a removed category's page goes too.

`index.md` isn't generated. It stays frontmatter only (`title`, `order`): the website loads a page as `<slug>.md`, and gives a section's `index.md` the slug `catalogue`, so a body there would be unreachable. That's why the content is in `overview.md`, as in `flow/apis/`.

## notes.json

```json
{
  "categories": {
    "<Category>": {
      "level": "note | warning",
      "page": "Shown at the top of the category page.",
      "task": "Shown under each task in the category.",
      "overview": "Shown under the table in overview.md."
    }
  },
  "tasks": {
    "<slug>": [
      {
        "revisions": "all | [1, 2]",
        "level": "note | warning",
        "defaultImage": "boomerangio/task-flow:3.3.0",
        "text": "The note, in Markdown."
      }
    ]
  },
  "usage": {
    "<slug>": {
      "revision": 2,
      "example": {
        "note": { "level": "note | warning", "defaultImage": "boomerangio/task-flow:3.3.0", "text": "Optional." },
        "scenario": "One or two sentences: the job the example does.",
        "params": [
          { "field": "**Task name**", "value": "`build`" },
          { "name": "script", "value": "The script below" },
          { "name": "workflowRef", "label": "Workflow", "value": "A label the editor shows instead of the seed's" }
        ],
        "code": [ { "for": "script", "lang": "sh", "text": "The param's full value, for a value too long for a table cell." } ],
        "results": [ { "name": "filename", "value": "What the result holds after this example." } ],
        "outcome": "What happens when it runs, and anything else the reader needs."
      },
      "errors": [
        { "symptom": "What you see, quoting the message.", "cause": "Why.", "fix": "What to do.", "defaultImage": "Optional." }
      ]
    }
  },
  "migrationTasks": [
    { "source": "<path to the migration>", "task": { "name": "", "type": "", "status": "" }, "revision": { "...": "the same shape as a seed revision" } }
  ]
}
```

- `revisions` says which revisions a note is about. The page shows the latest revision, but a note can describe an older one that a saved workflow may still be pinned to, such as the revisions that do nothing.
- `defaultImage` applies the note only while the seeded `default.image` is that image. When the default moves, the note is skipped with a warning. Remove it once the defect is fixed.
- A note renders as a GitHub alert: `> [!NOTE]`, or `> [!WARNING]` when its `level` is `warning`.
- Write notes to the docs voice in `.claude/skills/flow-tech-writer/voice-and-tone.md`. Quote labels verbatim from the seed, and link the matching section of `flow/introduction/known-issues.md`. Links are relative to `flow/catalogue/`.

### usage: examples and common problems

`usage` gives the most-used tasks a worked example and their common failures, rendered under the task's entry as "Example" and "Common problems". Values are Markdown, written as they should appear; only pipes are escaped and line breaks become `<br>` in a table cell.

- **`revision`** is the latest revision the entry was written for. When the seed's latest revision differs, the generator warns: re-check the example, then update the number.
- **`example.params`** are the fields the example sets, in the editor's order. A row with `name` is a param of the latest revision: the generator shows its seed label in bold, or `label` when the editor shows a different one (Run Workflow's **Workflow** picker). A row with `field` is anything else, such as **Task name** or **Result Parameters**, written as it should appear.
- **`example.code`** shows a param's whole value as a code block under its label, for a script, prompt or payload.
- **`example.results`** are what the results hold. When the latest revision declares results, each name must be one of them; a task that declares none, such as Execute Shell or Run Workflow, may name any, as Flow allows a reference to.
- **`errors`** are 2 to 4 failures, as symptom, cause and fix, rendered as a table. Quote the message the reader sees.
- **`defaultImage`**, on `example.note` or a problem, works as on a task note: it's shown only while the seeded `default.image` is that image.

The generator exits 1 when an entry names a task that isn't in the palette, a param the latest revision doesn't have, or a result it doesn't declare, or when a problem lacks its symptom, cause or fix.

Base each example on what a tutorial or guide ran live, and each claim about behaviour on the task's source: the engine in `flow.service.workflow` for the types Flow runs itself, and `boomerang-io/tasks` at the default image's tag for the rest.

## At each release

1. Regenerate with the new tag and read the warnings.
2. Look for a new migration that adds a task outside the seed: `git -C ../flow.service.workflow log <previous-tag>..<tag> -- service-core/src/main/java/io/boomerang/migration/`. Add it to `migrationTasks`.
3. Review every note against the release and the known issues. Remove a note whose defect is fixed, and add one for a new task defect.
4. Review every `usage` entry the generator warns about, and any whose task image or engine code changed: check the example still works and each problem still happens, then update its `revision`.
5. If a category disappears or is renamed, its page URL changes. Fix inbound links to it.
6. Check every link and anchor in `flow/catalogue/` resolves, then review the diff.
