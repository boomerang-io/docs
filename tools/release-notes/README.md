# Release notes generator

`generate.py` writes `flow/introduction/release-notes.md` from `CHANGELOG.md` in `boomerang-io/flow.service.workflow` at a tag or branch. Run it at each release, as you regenerate the task catalogue and the API reference. It needs Python 3.9 or later and git, and uses only the standard library.

The release notes are the complete record, release by release. `flow/introduction/whats-new.md` stays the hand-written story of a major release. Each page links to the other.

## Run it

From the docs repo root:

```bash
git -C ../flow.service.workflow fetch --tags
python3 tools/release-notes/generate.py --flow-repo ../flow.service.workflow --ref 5.0.0-beta.39 --version 5.0.0
```

| Option | Default | What it does |
| --- | --- | --- |
| `--flow-repo` | required | A clone of `flow.service.workflow`. The working tree isn't read, so it can be on any branch. |
| `--ref` | required | The tag, such as `5.0.0`, or the branch to read `CHANGELOG.md` at. |
| `--version` | required | A version heading to publish, such as `5.0.0`, which matches `## Unreleased: 5.0.0` or `## 5.0.0`. Repeat it to publish more than one. Every released section is published as well. |
| `--out` | `flow/introduction/release-notes.md` | The page to write. |
| `--check` | off | Writes nothing. Exits 1 when the page differs from what the ref generates. |

It prints, for each section, whether it's released, its number of Upgrading items and how many it marked **Breaking**, then how many links it pointed at GitHub. It exits 1 without writing anything when git can't read `CHANGELOG.md` at the ref, or a `--version` names no section.

## What it reads

`git show <ref>:CHANGELOG.md`. Each `## ` heading starts a section, and each `### ` heading a subsection. The CHANGELOG's title and introduction are left out.

A section heading is read for:

- **The version:** the first semver in it, such as `5.0.0` or `5.1.0-beta.2`.
- **Unreleased:** the word "Unreleased" anywhere in it, as in `## Unreleased: 5.0.0`.
- **The date:** an ISO date anywhere in it, as in `## 5.0.0 - 2026-11-20` or `## [5.0.0] (2026-11-20)`.

A heading with neither a version nor "Unreleased" is skipped with a warning.

## What it writes

One page: frontmatter (title "Release notes", order 7, the `DESCRIPTION` constant, and `verified`, the `--ref` quoted, when `--ref` is a tag; the website shows it as "Verified against Flow …", so a branch, which moves, gets none), the comment `<!-- Generated by tools/release-notes/generate.py from flow.service.workflow <ref>. Don't edit by hand. -->`, a short introduction that links to What's new, then one `## <version>` section per published release, in CHANGELOG order, newest first.

Each section starts with one line:

| The section is | The line says |
| --- | --- |
| Released, with a date in its heading | "Released 20 November 2026." and a link to `https://github.com/boomerang-io/flow/releases/tag/<version>` |
| Released, with no date | The link to the GitHub release |
| Unreleased | A note that the version isn't released yet, and which tag or branch the notes are from. There's no link to the version's GitHub release, which doesn't exist yet. |

The release skill in `flow.service.workflow` tags first and moves the CHANGELOG section under its version afterwards, so the release tag itself still reads `## Unreleased: <version>`. When `--ref` is the tag that `--version` names, the section counts as released, dated from the tag.

Then the subsections, in the order Upgrading, Added, Changed, Fixed, then any other subsection in CHANGELOG order. Their text is kept verbatim, internal paths, change units and decision dates included, because the CHANGELOG is the product's record. Two things change:

- **Breaking** labels on Upgrading items, described below.
- **Links into the Flow repo.** A relative Markdown link, or a reference definition, such as `[README](README.md#upgrading-from-v3)`, becomes a GitHub URL at the ref: `https://github.com/boomerang-io/flow/blob/<ref>/README.md#upgrading-from-v3`. A link to `#anchor` points at the CHANGELOG. For a branch, the URL uses the commit the branch points at, so it doesn't drift. External links, code spans and fenced code are left alone. The CHANGELOG at 5.0.0-beta.39 has no Markdown links: its paths are in code spans and stay as text.

### Breaking

An Upgrading item is marked **Breaking** when its text asks the operator to act. The item's text stays as written; the label and a link go on a line of their own at the start of the item:

```markdown
- **Breaking:** see [Upgrade from v3](../hosting/upgrading).
  **The dispatcher takes service-core's address as one URL.** `flow.engine.service.host` is gone: set
```

The generator reads the item as prose, with emphasis and code spans removed, and marks it when either holds:

- **An instruction.** A sentence or clause starts with a verb such as set, remove, add, give, move, export, check, copy, route, mount, send or trust. A clause is split at `.`, `:`, `;`, `!` and `?`, and a leading phrase such as "Before a v3 upgrade," or "In the Slack app's settings," is skipped first. "Change unit `_00…`" names a migration and isn't an instruction.
- **An obligation or a precondition.** The item says *must* or *need(s)* (not "no longer needs"), says something stops startup or is refused at startup, or speaks to "a client that…".

The verb list is `IMPERATIVES` in `generate.py`, and the other signals are `OBLIGATION`. Read every Breaking mark in the diff at each release: a heuristic can miss an item, or mark one that only describes new behaviour.

The link depends on the release:

| Release | Breaking items link to |
| --- | --- |
| 5.0.0, the release a v3 install upgrades to | [Upgrade from v3](../../flow/hosting/upgrading.md) |
| Any later release | [Upgrade between v5 releases](../../flow/hosting/rolling-upgrades.md), unless the item mentions v3 |

At 5.0.0-beta.39, 22 of the 31 Upgrading items are marked Breaking.

## At each release

1. Tag the release in `flow.service.workflow`, then fetch the tags.
2. Regenerate at the release tag: `--ref 5.0.1 --version 5.0.1`. Earlier released sections come along.
3. Read every **Breaking** mark against its item. If one is wrong, change the signals in `generate.py` rather than editing the page.
4. Check every link and anchor in the page resolves, then review the diff.
5. Update What's new by hand for a release that changes the story.
