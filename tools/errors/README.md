# Error code reference generator

`generate.py` writes `flow/introduction/error-codes.md` from `boomerang-io/flow.service.workflow` at a release tag: every error code the API returns, and every status reason a task or run ends with. Run it at each release, as you regenerate the API reference and the catalogue. It needs Python 3.9 or later and git, and uses only the standard library.

## Run it

From the docs repo root:

```bash
git -C ../flow.service.workflow fetch --tags
python3 tools/errors/generate.py --flow-repo ../flow.service.workflow --tag 5.0.0-beta.39
```

| Option | Default | What it does |
| --- | --- | --- |
| `--flow-repo` | required | A clone of `flow.service.workflow`. The working tree isn't read, so it can be on any branch. |
| `--tag` | required | The release tag the docs describe. |
| `--out` | `flow/introduction/error-codes.md` | The page to write. Links are checked as if it sat in `flow/introduction/`. |
| `--notes` | `tools/errors/notes.json` | The hand-kept notes. |
| `--check` | off | Writes nothing. Exits 1 when the page differs from what the tag generates. |

It prints the number of error codes, how many have notes and how many aren't returned, and the number of status reasons with notes. Warnings go to stderr. It exits 1 without writing when:

- a source file is missing or doesn't parse, or `notes.json` isn't valid JSON;
- a `notes.json` key isn't a reason in `BoomerangError`, or a status reason that isn't in `StatusReason.java`;
- an error has a code that no area rule covers, or an HTTP status the generator doesn't know;
- a link on the page doesn't resolve to a file, or an anchor to a heading in it.

## What it reads

All with `git show <tag>:<path>`, unless noted:

| Source | For |
| --- | --- |
| `service-core/src/main/java/io/boomerang/common/error/BoomerangError.java` | Each error's enum name, code, reason and HTTP status. |
| `service-core/src/main/resources/messages.properties` | Each reason's message. `{0}`, `{1}` and so on show as `{…}`. A reason with no message shows "No message available", as the API answers. |
| `git grep` of `service-core/src/main/` | Which errors service-core raises. A constant referenced only in `BoomerangError.java`, in a comment, or to read it (`BoomerangError.X.getReason()`) counts as not returned, and the page marks it **Not returned in this release**. |
| `service-core/src/main/java/io/boomerang/common/model/StatusReason.java` | The status reasons, in declaration order, and the `REQUEUEABLE` and `NOT_RETRIABLE` sets. |
| `dispatcher-sdk/src/main/java/io/boomerang/dispatcher/sdk/StatusReason.java`, and `git grep` for `StatusReason.X` in service-core | Who sets each reason: a dispatcher (in the SDK), Flow (set in service-core), or both. |
| `service-core/src/main/java/io/boomerang/engine/EngineConstants.java` | `MAX_RETRIES`, the requeue budget, shown on requeued reasons and substituted for `{requeueBudget}` in notes. |
| `specifications/dispatcher-contract.md` | Its requeue table under "Ending". The generator warns when it doesn't list exactly `REQUEUEABLE`. |

The reason, not the enum name, is what the API returns in `reason` and what the page and `notes.json` use. Six differ, such as `WORKFLOW_INVALID_REF`, whose reason is `WORKFLOW_INVALID_REFERENCE`.

## What it writes

One page, with the frontmatter `title: Error codes`, `order: 4`, `description` (the `DESCRIPTION` constant) and `verified`, the `--tag` value quoted, which the website shows as "Verified against Flow …". Then the comment `<!-- Generated by tools/errors/generate.py from flow.service.workflow <tag>. Don't edit by hand; edit tools/errors/notes.json. -->`, then:

- a lede, the lookup tip, and how to read an entry;
- one section per area, each entry under a `###` heading of its reason: the HTTP status and code (naming any reason that shares the code), the message verbatim, then **Why it happens**, **What to do** and **Related** from `notes.json`. An entry without notes gets a "See" link to its area's page. Within an area, entries are in code order, with the ones not returned last;
- **Task and run status reasons**: one entry per reason, with who sets it, whether Flow requeues it, whether task retries apply, then **What it means**, **What to do** and **Related** from `notes.json`;
- **Next steps**.

### Areas

`AREA_RULES` in `generate.py` places each error, first match wins, by enum name prefix and code range, and gives the "See" link for entries without notes:

| Area | Holds |
| --- | --- |
| Workflows | 12xx `WORKFLOW_*`, and `WORKFLOW_*` below 1000 |
| Runs | 13xx runs, 16xx actions, 17xx schedules, 20xx artifacts |
| Tasks | 14xx tasks, 15xx task runs, 21xx dispatchers |
| Workspaces | 11xx, and `QUOTA_*` |
| Parameters | `PARAM_*` (12xx) and `PARAMS_*` (18xx) |
| Tokens and auth | `AUTH_*`, `TOKEN_*`, `USER_*`, `PERMISSION_DENIED` |
| Settings | `SETTINGS_*` |
| Integrations | 19xx |
| Query | `QUERY_*`, and the generic `UNABLE_PATCH_REL`, `TOO_MANY_REQUESTS`, `DATA_CONVERSION_FAILED` |

A new code that no rule covers stops the generator: add a rule, so every range gets a deliberate home.

## notes.json

```json
{
  "errors": {
    "<REASON>": {
      "why": "Why it happens, in Markdown.",
      "do": "What to do.",
      "related": [{ "text": "Link text", "link": "../fundamentals/runs#timeouts" }]
    }
  },
  "statusReasons": {
    "<StatusReason>": {
      "meaning": "What it means.",
      "do": "What to do.",
      "related": [{ "text": "Link text", "link": "../guides/retry-a-run" }]
    }
  }
}
```

- Key errors by reason, as the API returns it. A key that's an enum name stops the generator and names the reason to use.
- `related` is optional. Links are relative to `flow/introduction/`, without `.md`; `#runs` and other anchors on the page itself work too.
- `{requeueBudget}` in any text becomes `EngineConstants.MAX_RETRIES`.
- Write to the docs voice in `.claude/skills/flow-tech-writer/voice-and-tone.md`. Quote UI labels in bold, exactly as the webapp shows them, and check each claim against the code at the tag: the throw sites of the error, not only its message. Where the message is wrong, say so, as for `TOKEN_INVALID_PERMISSION` and `USER_UNABLE_TO_DELETE`.
- A note for an error that isn't returned is still shown, with a warning.

At 5.0.0-beta.39, 78 of the 110 codes have notes, and all 29 status reasons do. The codes without notes are mostly internal or rare: blank-ID requests, template links, Google and Microsoft field values.

## At each release

1. Regenerate with the new tag and read the warnings.
2. Diff `BoomerangError.java`, `messages.properties` and `StatusReason.java` against the previous tag: `git -C ../flow.service.workflow diff <previous-tag> <tag> -- service-core/src/main/java/io/boomerang/common/error/ service-core/src/main/resources/messages.properties service-core/src/main/java/io/boomerang/common/model/StatusReason.java`.
3. Write notes for new user-facing codes and reasons. Re-check every note whose code's throw sites changed, and remove a note whose code is gone.
4. Check each "Not returned in this release" marker that changed.
5. Review the page diff. Inbound links to `error-codes#<reason>` use the lowercase reason as the anchor, such as `error-codes#quota_exceeded`.
